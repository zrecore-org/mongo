# MP14a: extension spike (standalone, outside src/)

Registered 2026-11-15 before any code. Lives in this fork (not in zrecore-org/exactmesh) because the Extensions API headers are SSPL-1.0 (`src/mongo/db/extension/public/api.h`: `SPDX-License-Identifier: SSPL-1.0`) and exactmesh is Apache-2.0. Whether anything built against these headers may be distributed, and under what terms, is a legal question for the owners; this POC does not decide it. Nothing under `src/` changes. All build outputs and downloads go under `./storage` (git-ignored, external volume); the internal disk has about 11 GiB free and must not drop below 5 GiB.

## Question
Can a MongoDB extension (a shared library loaded with `--loadExtensions`, C ABI only, no `mongo/base`) register one aggregation stage that receives batches of documents with packed triangle meshes, calls our exact mesh code, and returns per-document results, and what does the Extensions API force on us (language, batching, deadlines and kill, error handling, allocator, symbol visibility, a GPU context living in the same process)?

## Method (steps, in order)
1. Read `src/mongo/db/extension/README.md`, `public/api.h`, `public/api_contract.h`, `sdk/`, `test_examples/` (especially the deadline example) and the IDL files. Record the API version (1.0 at the time), the stage kinds (source, transform, desugar), how a stage receives a batch, ownership and status rules, how errors cross, how deadlines and killOp reach the extension.
2. Language question: does the tree ship Rust bindings? (The README says only Rust extensions are supported in production and the Search team owns the Rust SDK; the C++ SDK is for internal tests.) Record what exists locally and what does not; do not fetch anything unpinned.
3. Build a minimal extension `.so` (or `.dylib` on macOS) against the public C headers only, exporting `get_mongodb_extension_versions` and `get_mongodb_extension`, registering one transform stage `$meshVolume` that takes documents with a BinData field holding a packed triangle mesh (format defined in this POC: little-endian header with vertex and triangle counts, binary64 vertices, uint32 indices) and returns the exact signed volume as a decimal string of the exact rational and as a binary64 correctly rounded from it.
4. Write a small fake host (portal, getNext, batches, deadline and status/ownership rules) to drive it, because a full `mongod` build is heavy. The exact volume must match the exact oracle of the exactmesh repo (copy the oracle code under `poc/gpu/extension/` with provenance; do not add an exactmesh dependency).
5. Probe the integration questions with one probe each (label verified or unverified): symbol conflicts with a host that links `mongo/base` (is `-fvisibility=hidden` plus a version script enough); a statically linked C++ mesh library inside the extension; dlopen of a Vulkan loader from inside the extension (use the MoltenVK/lavapipe present locally; report only whether instance creation works inside the host process, no performance claims); the `--allocator=system` requirement (`bazel/transitions.bzl`) read from source; how a stage batches N documents into one call; how a deadline reaches the extension and what a well-behaved stage does; planted fault handling (below).
6. Optional last step, **reported, not gating**: load it in a real `mongod`. Only if the disk check allows: Bazel output root must be on the external volume (`--output_user_root=/Volumes/CrucialX9/Projects/mongo/storage/bazel`), expect tens of GB and a long build; stop and report if free space on the internal disk drops below 5 GiB. If skipped, say so.

## Bars (hard unless marked reported)
1. The extension loads in the fake host, reports the right API versions, registers the stage; the host rejects a planted extension with a wrong major version cleanly.
2. Batching: N documents (N = 1, 10, 1000, 100000 small meshes) in one stage invocation return N results in order; one batch call for the GPU-shaped path (a single call receives all documents of a batch), not one call per document, is demonstrated (report the call count).
3. Correctness: the returned exact volume equals the exact oracle on every corpus mesh the POC uses (spheres, tori, boxes, nested cavities, 1e3 random closed meshes); 0 wrong; documents that are not meshes or are open meshes produce a clean per-document error status, not a crash.
4. Errors cross the boundary without C++ exceptions escaping: a planted C++ throw inside the extension is caught at the boundary and returned as a status.
5. Planted crash (segfault in the extension) and planted timeout (the extension loops past the deadline): the fake host demonstrates what the API contract provides for each; what is NOT survivable in-process (a segfault takes the host down) is stated plainly, with the mitigation options (subprocess worker, circuit breaker) described, not implemented.
6. Planted mutants of the volume code (no exact accumulation: plain double sum; wrong sign; dropped last triangle) are each caught by the correctness bar.
7. Reported (not gating): language verdict (C ABI directly vs Rust bindings), symbol-conflict probe results, Vulkan-in-process result, the real-`mongod` load result or why skipped, size and build effort.

## Out of scope
GPU performance, booleans in the extension, security review, GPG signing of the extension, changes under `src/`, any upstream contact.

# MP14c: GPU enablement through the mongod configuration (registered 2026-11-16 before any code)

Owner requirement (2026-11-15): 3D GPU acceleration is off by default and can be enabled through MongoDB configuration. Research result: the server passes the YAML `extensionOptions` map of the extension's config file (`/etc/mongo/extensions/<name>.conf`, or `extensionsConfigPath`) to the extension through the host portal (`get_extension_options`, api.h:1289), serialised with `YAML::Dump`; the extension cannot register server parameters. This item builds that gate in `meshvol_ext`. It adds NO GPU kernel: `$meshVolume` stays on the CPU, so the only thing the gate controls is the capability probe and the reported engine. A kernel stage is a later item.

Options (flat map, strict): `gpu: true|false` (default false), `gpuRequired: true|false` (default false). Unknown key, non-boolean value, nested or non-`key: value` line, or `gpuRequired: true` with `gpu` not true: `initialize` returns an error (the server treats any load failure as fatal, by design: a wrong config must not start silently).

## Bars
1. Default off: no options (empty string and `{}`) and `gpu: false`: initialize succeeds, the Vulkan loader is NOT opened (probe counter 0), config probe reports `gpuRequested=false`, `engine="cpu"`.
2. `gpu: true` with a working Vulkan (lavapipe in the Linux container, MoltenVK on the M1): the probe runs once at initialize, `gpuReady=true`, `engine` still `"cpu"` (no kernel), and every `$meshVolume` result is byte-identical to the default-off run on the whole corpus.
3. `gpu: true` with no Vulkan loader (loader path made unavailable): initialize succeeds, `gpuReady=false`, a reason string is reported, results identical to default-off; with `gpuRequired: true` initialize returns an error status instead.
4. Strictness: each of unknown key, `gpu: maybe`, `gpu: 1`, an indented line, and `gpuRequired: true` without `gpu: true` makes initialize fail with a clear message (5 cases, all rejected).
5. Mutants (each must be caught by bars 1 to 4): option ignored (gpu always on), default flipped to on, gpuRequired ignored, strictness removed (unknown keys accepted).
6. Reported, not gating: a run in the fork's real `mongod` (needs the win machine and its turn) with `extensionOptions: {gpu: true}`; if not run, say so.

Out of scope: any GPU kernel inside the extension, speed, `mongod --setParameter` style options (not possible for extensions), secure-build signing.

## MP14c amendment 1 (2026-11-16, before further runs; from the aalbino-1b review)
Changes to the bars above; where they conflict, this wins.
- **Observability channel (was undefined):** the probe `config` of `$meshVolume` (a stage option, test-only like the other probes) and, in a real `mongod`, one log line at initialize through the host logger: `meshvolume: gpu requested=<b> ready=<b> engine=cpu reason=<text>`. The log line is what an operator sees.
- **Bar 1 add-on (independent of the extension's own counter):** after initialize with the default config, the Vulkan loader is not in the process image list (macOS `vmmap`/`_dyld_image_count`, Linux `/proc/self/maps`, checked from the fake host after load). Also a mutant that probes at static-initialiser time must be caught by this check, not by the counter.
- **Bar 3 add-on:** reason strings defined and tested for: loader missing, instance creation fails, zero physical devices, only a CPU or software device (`gpuReady` is true only for a non-CPU device type; lavapipe therefore reports `gpuReady=false, reason="software device only"`, and CI/lavapipe runs say so; that is a property of the gate, not a failure). Reason strings contain no paths.
- **Bar 4 add-ons (accept and reject cases, using text produced by the real `YAML::Dump`, not hand-written):** accept `gpuRequired: false` alone, `gpu: true` with `gpuRequired: true` (when ready), `gpu: false` with `gpuRequired: false`; reject `gpu:` (empty), `gpu: ~`, `gpu: yes`, `gpu: True`, `gpu: "true"`, key `GPU`, a duplicate key, tab indentation. Document what the server does first for duplicate keys. Inputs are generated by a small C++ program linked with yaml-cpp from the fork tree, or, if that is not buildable standalone, taken from `mongod`'s own conf parsing in the real-mongod run.
- **Probe deadline and crash (new bar 7):** a planted hang in the probe is bounded (the probe runs in a helper thread; initialize returns an error status after a stated limit, default 10 s, and `gpuReady=false` unless `gpuRequired`, in which case it fails). A probe that crashes inside a driver is NOT survivable in-process (MP14a bar 5); this is stated plainly and the subprocess-probe option is described, not built.
- **Bar 6 promoted to gating for the default-off case:** on the fork `mongod` (win machine, Docker, CPU): no `extensionOptions`, `extensionOptions: {}` and `gpu: false` all load, the log line shows `requested=false`, no Vulkan loader in `/proc/<pid>/maps`; `gpu: true` on lavapipe loads and logs `ready=false reason="software device only"`; `gpu: true`, `gpuRequired: true` makes the server refuse to start with the reason in the log. The GPU-device case on the 4060 Ti through Dozen stays reported, not gating.
- **Fake host must model fatal:** the gpuRequired-failure bar asserts the fake host aborts the load, not only that initialize returned an error status.
- **More mutants (one per case):** probe at static-init, probe error swallowed (`gpuReady=true` on failure), empty reason, each strictness case removed alone, `gpuRequired` default flipped to true, `engine` hard-coded to "gpu".
- **Out of scope, one line each:** the process environment (`VK_DRIVER_FILES`, `VK_ICD_FILENAMES`, layers) can make the Vulkan loader load arbitrary libraries into `mongod` (security-review item); loader unload (the instance is destroyed, the loader is never `dlclose`d); initialize called twice (the probe result is cached per process).
- Bar 2 says only that the gate does not disturb results; it is no evidence of GPU use.

# MP14d: `$meshContains`, a stage whose GPU path is enabled by the MP14c gate (registered 2026-11-16 before any code)

Why: with MP14c `gpu: true` only reports capability (`engine=cpu` always). This item gives the gate something to switch, and tests the G4 conclusion (2x only with large amortised batches, CPU default) inside a real `mongod`. Scope is deliberately small: one stage, one kernel that already exists and is verified (MP12c BVH point-in-solid, exactmesh `gpu/pip_bvh.comp`, Apache-2.0, copied here with provenance; Apache code inside this SSPL tree is allowed per `LICENSING.md`).

Stage: `{$meshContains: {mesh: "<field>", points: "<field: array of [x,y,z] binary64>", output: "contains"}}`. Per document: array of verdicts, one per point: `IN`, `OUT` or `ON` (on the boundary), exact (the exact predicate decides; the GPU filter may only answer IN/OUT when certain and otherwise defers to the exact CPU path, as MP12c/MP13 do). The CPU path (exact orient3d / BVH walk) is the default and the oracle; the GPU path runs only when `gpuReady` and the batch is large enough (a configurable threshold, default conservative), per MP13's fallback, circuit breaker and shadow check design.

## Bars
1. CPU path correctness: verdicts equal the exact oracle on the MP12e corpus (60 models, 540k queries; hash `c2800183f077073a` over the verdict array as in MP12c) and on the unit corpora (spheres, tori, nested cavities, vertex-on-boundary cases); 0 wrong; errors per document as in `$meshVolume` (closed-mesh rules).
2. GPU path (only when `gpu: true` and `ready`): verdict array byte-identical to the CPU path on the same corpus (same hash), 0 false definite, on the M1 (MoltenVK) and the 4060 Ti (Dozen in the container); with `gpu: false` or not ready the GPU code is never entered (counter 0, no Vulkan image loaded: MP14c bar 1 still holds).
3. Fallback: a planted device failure (device lost, shader failure, timeout) mid-batch returns the CPU result for that batch with a log line, never a wrong or missing verdict; the breaker opens after N consecutive failures and stays open until restart; shadow check mismatch (planted) disables the GPU path and the stage returns the CPU result.
4. Mutants (each caught by bars 1 to 3): GPU verdict trusted without certainty check, shadow check removed, breaker never opens, threshold ignored (GPU used for tiny batches), wrong sign/orientation in the CPU path, boundary treated as IN.
5. Real `mongod` (win machine, container): bars 1 and 2 through an aggregation with `batchSize` large and small; server healthy after planted faults; on lavapipe `gpu: true` stays on CPU (`software device only`, so the GPU path is not entered); on the 4060 Ti via Dozen the GPU path runs and results are identical. Reported, not gating: any speed number (G4 says amortised only; no speed claim beyond a measured, labelled table).
6. Memory and lifetime: Vulkan objects created lazily on first GPU-eligible batch, destroyed at extension shutdown (instance destroyed, loader never `dlclose`d); no leaks in the stage-object accounting of MP14a.

Out of scope: booleans, distance queries, sharded topologies, signing/release builds, any change under `src/`.
Order of work: (1) CPU path and bar 1 in the fake host; (2) GPU path and bars 2 to 4 on the M1; (3) real `mongod` runs on win (CPU first, then a GPU turn).

## MP14d amendment 1 (2026-11-16, before any GPU code; from the advisor and the step-1 work)
- **Bar 1 reference (was wrong):** MP12c's `c2800183f077073a` hashes the three-class FILTER verdicts (OUT/IN/UNCERTAIN), not resolved verdicts. The `$meshContains` reference is the resolved exact verdict array. Measured: MP12e list (60 models, 540,000 queries, MP12c classes seeded from the model id), oracle = exactmesh `cpu/pip_hardened.h` with candidates from exactmesh's independent `bvhref` BVH: OUT 330,648, IN 140,916, ON 68,436 (equals MP12c's "exact-boundary 68436"), FNV-1a over the verdicts (0/1/2 as the verdict value, model order then class order) = **`ae59d9976297a67b`**. The extension's CPU path (own BVH, filtered predicates with exact fallback) gives 0 disagreements on all 540,000 (`real_contains.cpp`, log `docs/logs/mp14d_real_contains60.log` in exactmesh). Bar 2 compares the GPU path's final output to this hash.
- **CPU path now has a BVH** (the all-triangles path stays as the reference): a naive CPU baseline is the artefact this project already caught once (MP13). The BVH is the fair CPU baseline for any speed table.
- **Extreme exponents:** the float filter is used only when every difference is zero or inside [1e-150, 1e150] (orient2d) / [1e-90, 1e90] (orient3d), else the exact integer path. Verified against the hardened oracle on subnormal (2^-1060), 2^-600, 2^600 and 2^1000 meshes; the guard is defensive: the corpus does not distinguish it from no guard (mutant NO_WINDOW is not caught, recorded as informational).
- **Real scope of the GPU path (replaces "one kernel that already exists"):** MP12c's pipeline is LBVH build on the device (Morton codes, radix sort, tree build, box fit: `lbvh_morton`, `sort_*`, `lbvh_build`, `lbvh_fit`), host-side outward-rounded ray boxes, the soft-binary64 filter kernel `pip_bvh.comp` (with `f64soft.inc`, SSPL-derived, and the `*_filter.inc` includes), and UNCERTAIN queries re-decided by the exact CPU path. In the extension this needs a Vulkan host runtime (instance/device/pipelines/buffers via the loader at run time), the SPIR-V embedded in the library, and the host orchestration. Steps: (2a) device runtime and a trivial kernel inside the extension, (2b) BVH build on the device or on the CPU with upload (decide by measurement; CPU build is allowed and simpler), (2c) the filter kernel and UNCERTAIN resolution.
- **Document-size reality:** a BSON document is at most 16 MiB: at most about 650k points as BinData (24 bytes per point), far fewer as arrays. MP12c's 2x regime was about 1e6 queries against a resident mesh, which one document cannot carry, and across documents the stage has no mesh-identity cache. Therefore MP14d proves correctness and that the gate switches an engine; any speed number it reports is below the G4 regime by construction and is labelled so. Mesh dedup across documents is out of scope unless added later by its own plan.
- **Concurrency:** `get_next` runs on mongod query threads. One process-wide mutex serialises Vulkan build/submit/wait (a queue is not thread-safe); CPU path is unaffected. Chosen: mutex, not a worker thread.
- **Finite fence wait:** `vkWaitForFences` with a timeout derived from the stage deadline (capped); a timeout counts as a device failure, the batch falls back to the CPU path, the breaker counts it. An infinite wait would be an unkillable stage (MP14a showed the host cannot interrupt a stage mid-call).
- **Output shape:** the stage writes a string of `O`/`I`/`B` (one character per point), not an array of verdicts; the plan text "array of verdicts" is corrected to match.
- **Real-mongod bars (5)** need `models60` on the win machine: kept (the earlier "can go" was retracted).
