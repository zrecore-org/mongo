# MP14a results: extension spike (standalone, outside src/)

Executed 2026-11-14 against the plan in `PLAN.md` (unchanged; bars not edited). Nothing under `src/` was touched, nothing was committed. Platform: macOS arm64 (Darwin 27), Apple clang 21, C++20. All build outputs and logs are in `storage/extension_build/` (git-ignored).

Reproduce: `poc/gpu/extension/run_all.sh` (about 5 s to build everything, about 3 s to run all bars; the Vulkan probe additionally waits for the shared GPU lock, and was not run in this session).

## What was built (all under poc/gpu/extension/)

Size: extension `libmeshvol_ext.dylib` 199,688 bytes (-O2, Boost.Multiprecision statically inlined; `otool -L` shows only libc++ and libSystem). About 1,800 lines of C++ in total (extension 634, core 200, bson 109, host 811, bad 63). Build effort: one `clang++` line per artefact, about 3 s for the extension.

Pack format (defined here, identical to exactmesh `MSH1`): little-endian u32 magic `0x3148534d`, u32 nv, u32 nt, nv*3 binary64, nt*3 u32 indices, in BSON BinData subtype 0. Stage: `{$meshVolume: {input: "mesh", output: "meshVolume", batchSize: 1024}}` adds `meshVolume: {exact: "<p/q>", approx: <double>}` or `meshVolume: {error: {code, reason}}` to each document. The exact value is a reduced rational string `p/q`: V = (6V)/6 so a decimal expansion generally does not terminate and a decimal string of the exact rational does not exist; `approx` is the binary64 correctly rounded from it.

## Bars (hard)
Totals from `fakehost all`: **60 PASS, 0 FAIL** (log `storage/extension_build/all_run_logged.log`).

1. **Loads and registers; wrong major rejected cleanly: PASS (11/11).** Extension advertises 1.0, negotiated 1.0, returned `extension->version` 1.0, registered `$meshVolume`. Planted rejections, each with the host's reason and no crash: only major 2; minor 1.1 above host 1.0; null/empty version list; returns extension claiming 2.0 after negotiating 1.0; no `get_mongodb_extension` symbol; `initialize()` returns an error; major UINT32_MAX; missing file. Caveat: the fake host mirrors the real negotiation code by reading it (`load_extension.cpp:148-190`), it is not that code. One variant (non-null pointer with `len == 0`) was not separately planted: my "empty list" variant used a null pointer, which the real code rejects first.
2. **Batching: PASS (10/10).** N = 1, 10, 1000, 100000 small tetrahedra in one stage invocation return N results in input order (`_id` carried through) and each equals the oracle. Counts (`hostGetNext` / `sourcePulls` / `computeCalls`):
   N=1: 2 / 2 / 1; N=10: 11 / 11 / 1; N=1000: 1001 / 1001 / 1; N=100000: 100001 / 100001 / **1** (310 ms in the extension including BigInt arithmetic and BSON copy). With `batchSize=1024` and N=100000: 98 compute calls = ceil(N/1024); with `batchSize=1`, N=1000: 1000 calls. So a single call receives all documents of a batch when `batchSize >= N`; the host-to-extension edge itself stays one `get_next` per document (see API findings).
3. **Correctness: PASS, 0 wrong of 1,940 corpus meshes + 200 analytic.** Corpus: 240 boxes (incl. small-integer boxes), 100 UV spheres (a third centred at 1e8), 100 tori (half centred at 1e7), 100 nested cavities (box with box or sphere cavity, inner shell reversed), 1000 random closed meshes (subdivided octahedron, full-mantissa jitter, scales 2^-20..2^20, offsets up to 1e8), 200 random tetrahedra. Each is compared as an exact rational string against `oracle/exact.h` `exactVolumeTimes6` (/6), and `approx` is proven correctly rounded by exact rational comparison with both neighbouring doubles (ties to even). Independent analytic check: 200 boxes equal the exact product of side lengths (0 wrong). Error documents: 19 planted cases (missing field, string, int, BinData subtype 128, short header, bad magic, size shorter/longer than header, index out of range, NaN, Inf, open mesh, duplicated triangle, degenerate triangle, empty mesh, counts that overflow 32-bit math, truncated BSON, missing terminator) each placed next to a valid mesh in the same batch: all 19 give a per-document `{error: {code, reason}}`, status OK, neighbours correct, no crash.
4. **Exceptions do not escape: PASS (6/6).** Planted `std::runtime_error` in the batch compute, in `get_next`, in `parse`, in `open`: each returned as status code -1 with reason "caught C++ exception at the extension boundary: ...", 0 exceptions seen escaping by the host (try/catch around every call), extension counter shows 4 caught, stage works afterwards. Every status-returning vtable entry runs through one `guard()` with `try/catch(...)`.
5. **Crash and timeout: PASS (5/5, and the limits are stated).**
   - Segfault (`plant: segv`) in a forked child: child killed by signal 11. **Nothing in the API contract survives this: the whole host process dies.** Mitigations (described, not implemented): run the mesh code in a worker subprocess behind the extension (the extension stage only does IPC, so a worker crash becomes a status), with a restart policy; a circuit breaker that stops sending work to a worker (or stage) after N crashes or timeouts and returns errors fast; and keep the in-process part free of memory-unsafe code on untrusted input (the validator here bounds-checks everything).
   - Deadline, cooperative stage: deadline 100 ms, planted spin 2000 ms that polls `get_deadline_timestamp_ms` and `check_for_interrupt`: returned status 50 after 98 ms.
   - killOp, cooperative stage: kill flag set at 80 ms, seen through `check_for_interrupt` (code 11601), returned after 90 ms (453,283 interrupt checks in the busy loop, so poll at a sane rate).
   - Deadline, non-polling stage (`spinRude`): deadline 100 ms, host kill flag raised at 100 ms, stage busy-loops 600 ms: it ran to 599 ms, never called `check_for_interrupt`, and only noticed the deadline at its next checkpoint (error 50). **The deadline and kill are cooperative: the contract gives the extension `get_deadline_timestamp_ms` and `check_for_interrupt`, the host cannot preempt an extension thread, and an extension that does not poll stalls the operation (and its thread) for as long as it likes.** In real mongod this also holds locks and a connection thread for that time. Mitigation: bound every unit of work (poll between meshes and inside large ones) and, for uncooperative native code (GPU calls), a watchdog plus subprocess worker.
   - Info: with the boundary `catch` removed (variant `libmeshvol_nocatch`), an escaping exception takes a host without try/catch down with SIGABRT ("terminating due to uncaught exception"); a host that happens to have `catch(...)` around the call survives on this toolchain. The API says an escape is undefined behaviour; do not rely on it.
6. **Mutants caught: PASS (3/3, each at least 1 wrong).** Same corpus against separately built dylibs: plain double sum (mutant 1) 1882 wrong of 1940 (the 58 meshes it still gets right were not individually identified; the 40 small-integer boxes, where binary64 arithmetic is exact, are the obvious candidates); wrong sign (mutant 2) 1940 wrong; dropped last triangle (mutant 3) 1940 wrong. The clean build gives 0 wrong. (Counts include the 200-box analytic check, which is why they exceed the 1740 oracle mismatches for mutants 2 and 3.)

Ownership accounting at the end of the run: every returned ByteBuf destroyed (`liveBufs=0`), every heap status destroyed (`liveStatuses=0`), no stage object leaked (`liveObjs=1`, the probe pipeline's own exec stage).

## Reported (not gating)

### Language verdict
- **C ABI directly (what was built here) is workable, but the "C" header is not parseable as C.** `public/api.h` fails in C17 and C2x (`clang -x c-header`): errors at `api.h:245` (`::MongoExtensionLogType` scope qualifier), `:341`, `:362` (the `::`-qualified member types), plus `enum X : uint8_t` and the `#define[[MONGO_MOD_PUBLIC]]` fallback (a macro name that is not an identifier, which fails in C++ too when `mongo/util/modules.h` is absent). It compiles as C++20, and with `-I src` it pulls `mongo/util/modules.h` and `mongo/platform/compiler.h` (needs a C++ standard library). I used an empty stub `modules.h` in my own include directory to keep the public headers standalone (no `src/` change). The ABI itself is plain function-pointer vtables and POD structs, so a non-C++ language can implement it from a hand-port or from `bindgen` in C++ mode; but "C ABI" in the plan's sense (a C header) is not literally true of the shipped file.
- **Rust bindings: not present in this tree and not usable here.** `find src -name '*.rs' -o -name Cargo.toml` finds only mozjs/wasm shims (`src/mongo/scripting/mozjs/wasm/support/rust_shims`, `src/third_party/mozjs/.../gluesmith`); no Rust SDK for the Extensions API. `rustc` and `cargo` are not installed. `src/mongo/db/extension/README.md` says only Rust extensions are supported in production, the Search team owns the Rust SDK, and the C++ SDK is for internal tests; that SDK still depends on `mongo/base` (README note, SERVER-107651). `extensions/download_external_extension.py` only fetches prebuilt external extensions by sha256. Nothing was fetched.
- **Verdict for our code (exact mesh code is C++: Boost.Multiprecision, Geogram route):** write the extension in C++ against the public header only, do not use the SDK (it drags `mongo/base`), keep the extension a thin adapter (batch, validate, call the mesh library through a plain C-style interface), and treat language as not forced by the API: the boundary is C-compatible, so C++ with `extern "C"` entry points works. If Search's Rust SDK becomes the supported path, a Rust shell around a C-ABI mesh library would be the alternative; not evaluated beyond reading. Unverified: whether MongoDB would accept or distribute a C++ extension outside its own Rust-only production policy.

### API findings that force design
- **Batching is pull-one-document.** `MongoExtensionExecAggStageVTable::get_next` returns one document; the stage pulls from its source with `set_source` and one `get_next` per document. The GPU-shaped design therefore is: on an empty buffer pull up to K documents (copying each, because a source view is valid only until the next pull; my host poisons the previous bytes to prove the extension copies), make one batch call, serve results from the buffer. `set_batch_size` on the query execution context is for a *source* stage's batches, not for transforms. Read-ahead interacts with the deadline: the deadline is refreshed per getMore, and a large K means a long synchronous fill; the extension must check the deadline inside the gather loop and the compute.
- **Errors:** a non-OK status from `get_next` ends the whole operation, so per-document errors must live in the output document (done). Status ownership: the callee returns an owned status, the caller destroys it; OK is a non-null singleton with no-op destroy (`shared/extension_status.h`); I mirrored that.
- **Ownership:** output documents are returned as `kByteBuf` (host destroys) or `kByteView` (extension keeps valid until the next `get_next` or destroy). Input views from the source must be copied.
- **Allocator (read from source, not run):** `bazel/transitions.bzl:75-92` (`_extensions_transition_impl`) forces `//bazel/config:allocator = system`, `linkstatic=True`, `shared_archive=True`, `skip_archive=True`, `dtlto=False`, `pgo_profile_use=False` for extension builds; `src/mongo/db/extension/CLAUDE.md` repeats it. The rationale is not written in those files. What I can say from the API: all cross-boundary memory is owned through vtable `destroy` calls, so each side frees what it allocated and no allocator has to be shared; an extension must not assume the host's tcmalloc and must not replace global `operator new`.
- **Loading:** `dlopen(RTLD_NOW | RTLD_LOCAL)`, so the extension's symbols do not enter the global namespace and its dependencies are resolved at load. Signature validation (RNP/GPG) is skipped unless `extensionsSignaturePublicKeyPath` is set (insecure build) or required in secure builds (`host/signature_validator.cpp`); out of scope here.
- **Extension loading in mongod is Linux-only in this tree:** `src/mongo/db/extension/host/BUILD.bazel:171-175` defines `MONGO_HOST_EXTENSIONS_COMPATIBLE` only when not `not_linux` and not amazon_linux_2, and `load_extension.cpp:196` guards the loader with it.

## What was not run / not verified
- Real mongod, any Linux target, any sharded topology, getMore and deadline refresh across batches, `explain`, `$lookup`/`$facet` placement, query shape serialization (`get_query_shape` returns a placeholder), view handling, signature validation, ASAN/TSAN/valgrind runs of the extension, concurrency (one thread only in the extension; counters are atomics but no multi-threaded test).
- The fake host is written by me against the header and by reading `load_extension.cpp`; where the real host differs (for example how it treats a null status or how it sizes expanded arrays) results may differ.
- GPU and Geogram were not used in the extension; no performance claims.
- 1e3 "random closed meshes" are star-shaped jittered octahedron subdivisions, not arbitrary self-intersecting meshes; volume is defined for any closed oriented mesh and the oracle agrees on all of them, but non-manifold or self-intersecting-but-closed inputs were only covered for rejection (non-manifold edges), not for volume semantics.
- The extension rejects meshes that are not oriented closed 2-manifold edge-wise (every directed edge exactly once with its reverse exactly once); multi-shell and nested cavities pass. Whether that policy matches what the product wants (for example open meshes with a defined volume) is a decision, not tested.

## Open issues
- Legal: extension headers are SSPL-1.0; whether a built extension may be distributed, and under what terms, is for the owners (PLAN.md already states this).
- `modules.h` fallback `#define[[MONGO_MOD_PUBLIC]]` in `api.h`/`api_contract.h` is invalid whenever `mongo/util/modules.h` is absent: external developers need a stub or the real header. Worth reporting upstream by the owners (no upstream contact made here).
- In-process crash isolation is not provided by the API; a production design needs the subprocess-worker option (described only).
- Hot loops that call `check_for_interrupt` cost a host call and allocate a status each time in my implementation; a real extension should poll at coarse granularity.

## MP14b: the extension against STOCK release `mongod` binaries (2026-11-15; registered in exactmesh `docs/PLAN.md`, MP14b amendment)
Setup: stock MongoDB 8.2.2 and 8.3.0 Linux x86_64 (Ubuntu 22.04 builds from fastdl.mongodb.org; tarball sha256 35146f6b...5d4 and 688a5370...c3b9), run in WSL2 (Ubuntu 24.04, g++, no GPU involved) on the shared `win` machine, CPU only, started with `--setParameter featureFlagExtensionsAPI=true`. The extension was built there with g++ from this directory's sources against this tree's public headers (`libmeshvol_ext.so`, 196,864 bytes, sha256 7250e8c282e385bab8455f17d57228f8c614d289ab7e3be18c9e9e7c7d15576b, built in 9.6 s). Nothing was changed under `src/`, nothing under `/etc`, no sudo.

Results (bar 1, "loads or refuses with a recorded reason": refused, with reasons; bars 2 and 3 not reachable):
* **The three API versions differ.** This tree's `public/api.h`: MONGODB_EXTENSION_API 1.0 (1437 lines). Tag r8.3.0: 0.1 (1282 lines). Tag r8.2.2: 0.0.0 (269 lines, one stage type, NoOp; read from the tags on GitHub, headers kept in `storage/api_hdrs` of the exactmesh checkout). A 1.0 extension cannot be loaded by either release: a different major version means different struct and vtable layouts, so the extension was not patched to accept major 0.
* **8.2.2:** flag is `--extensions <path to .so>` (there is no `--loadExtensions`). The server reached `dlopen` and our `get_mongodb_extension`; our own check (`extension.cpp:629`) rejected the requested major version: log `Error loading extension ... code 21 "meshvolume: unsupported API major version requested"`, server exited 51 on startup.
* **8.3.0:** flag is `--loadExtensions <name>` (name only, no path separators) and the config file is read from the fixed path `/etc/mongo/extensions/<name>.conf` (there is no `--extensionsConfigPath`; the tree has one). The server stopped there: `code 11042900 "Loading extension 'meshvol_ext' failed: Expected configuration file not found at '/etc/mongo/extensions/meshvol_ext.conf'"`. Not retried: creating that directory on the shared Windows machine needs sudo and is outside what was authorised. The 8.3.0 binary contains both "Skipping signature validation" and the secure-mode message about `extensionsSignaturePublicKeyPath`, so whether an unsigned extension is accepted depends on how that binary was compiled; not determined.
* What this means for G5: stock releases cannot run an extension written for this tree's API; G5 needs either a `mongod` built from this tree (tens of GB, hours) or a port of the extension to a release's older API (different vtables; header diff 8.3.0 vs this tree is about 200 non-comment lines) and, for 8.3.0, a writable `/etc/mongo/extensions` and a signature answer. Neither was done.
* The Vulkan probe inside a real `mongod` and `$meshVolume` through a real aggregation (bars 2 and 3) were NOT run.
