# MP20: local patch of Geogram v1.10.1 for vertex-contact classification

Written by the main session from the sub-agent's report; set 4 tallies re-checked by me from the result TSVs; the patch hash and freeze order re-checked.
Plan and bars (registered before any work): `../../../PLAN.md` section MP20. Local patched copy only (`storage/mesh/mp20/geogram_patched`), never vendored, never sent upstream.

## Mechanism (sub-agent; instrumented copy plus source read; verified unless marked)
- Contact-only pairs record 0 intersections, so nothing links the two components. `classify()` casts one +z ray from each component's start vertex and that ray alone sets its inclusion bits.
- (a) The start vertex is corner 0 of the component's lowest-index facet. When it is the shared contact vertex, `orient_3d` is 0 and `orient_3d_SOS` decides **by pointer order**; the ray start gets a fixed perturbation independent of vertex labels, so the answer is not geometric. For vertex-vertex contact this gives A inclusion bits 2 (wrong) and B bits 0 (right). Not derived: why that direction is wrong for A. Unverified: the same address order on other platforms (observed on arm64 macOS only).
- `normalize_facet_vertices_order` in the prologue rewrites every facet's corner 0 as a function of vertex indices; that is why relabelling can move the start vertex. MP18's "triangle-order permutation falsified" finding looks invalid because of this normalisation (its probe was not re-run).
- (b) In `s3_twopoint_003` the start is the contact vertex under 3 fixed orders and 40 of 40 random relabellings (24 triangles instead of 28). Lower-index (A) vertices go to contact vertices (observed in traces, not read from source: `ComparePoints` has no index tie-break). A predictive probe (rotating B's triangle list) moved the start and fixed 2 of 4 rotations.
- (c) `nested_vertex_box5_000` starts at the contact vertex in 21 of 40 relabellings (wrong) and at a free vertex in 19 (right).

## Patch (`geogram_mp20.patch`, 126 diff lines, one file; sha256 4074ad1f...92e4, matches `FROZEN_SHA256.txt`, frozen 07:20:16Z before `gen_touch_set4.cpp` existed)
Only when a component's start vertex is shared with another component, the ray starts from the exact centroid of one of its own facets (preferring a facet with no shared vertex, falling back to the first facet when every facet touches a contact vertex, as in a two-contact tetrahedron). All other components are untouched.

## Caveats
- The curved-curved class has no unpatched failures, so set 4 does not discriminate there. Three `sliver_any` union rows are scored PASS with volume `close`, identical unpatched.
- Expectations in the contact families are generated by the same authors as the patch; the exact-volume and point-in-solid oracle is independent, and I independently confirmed one two-point failure with exact arithmetic (`../mp18/check_twopoint.cpp`).
- Pointer-order tie-breaking means the unpatched library's behaviour on contact depends on memory layout; the patched path removes that dependence only for the shared-start-vertex case. Cross-platform behaviour (x86_64, Linux) of the patched build is not tested.
- One machine (M1), Geogram v1.10.1 only, single thread.
