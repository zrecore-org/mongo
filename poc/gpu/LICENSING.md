# Licensing note: what SSPL-1.0 asks of us if we ship our own fork (2026-11-15)

This is a research note for the owners, not legal advice. Quotes are from `LICENSE-Community.txt` at the repository root (Server Side Public License, Version 1, October 16, 2018) unless another source is named. Where I could not fetch a source this session, the note says so and states nothing from memory.

## Facts that the scenarios rest on
- The fork is a work based on MongoDB's `mongod`, licensed SSPL-1.0. `src/mongo/db/extension/public/api.h` and `api_contract.h` are SSPL too (`api.h` line 2: `SPDX-License-Identifier: SSPL-1.0`).
- The licence offers "any later version" only if the Program says so (section 14: "If the Program does not specify a version number ... you may choose any version ever published by MongoDB, Inc."). I did not check each file's header for such a statement.
- Our own code in this repo is licensed as follows: Apache-2.0 for the shaders and the non-derived host files in `poc/gpu` (owner decision, 2026-11-15); SSPL for anything derived from MongoDB source and for `poc/gpu/extension/`; exactmesh is Apache-2.0.

## Scenarios
1. **Internal use only (we run it, we do not convey it, no third party uses it as a service).** Section 2: "you may make, run and propagate covered works that you do not convey, without conditions so long as your license otherwise remains in force", "subject to section 13". MongoDB's FAQ states that providing MongoDB "as a service internally or to subsidiary companies" is not making it available to a third party (FAQ page fetched 2026-11-15; the page is a summary, the licence text governs). Section 2 also allows conveying to others "for the sole purpose of having them make modifications exclusively for you, or provide you with facilities for running those works" under conditions.
2. **Conveying our own release binaries (downloads, customers, partners).** Sections 4 to 6, the GPLv3 mechanics. Section 5 (a) prominent notices that we modified it, with a date; (b) notices that it is released under this licence; (c) "You must license the entire work, as a whole, under this License to anyone who comes into possession of a copy ... This License gives no permission to license the work in any other way". Section 6: object code must come with the machine-readable Corresponding Source, by one of the listed routes, for example 6(d), "offering access from a designated place ... and offer equivalent access to the Corresponding Source in the same way through the same place at no further charge".
3. **Offering it to third parties as a service.** Section 13: "If you make the functionality of the Program or a modified version available to third parties as a service, you must make the Service Source Code available via network download to everyone at no charge, under the terms of this License." and "'Service Source Code' means the Corresponding Source for the Program or the modified version, and the Corresponding Source for all programs that you use to make the Program or modified version available as a service, including, without limitation, management software, user interfaces, application program interfaces, automation software, monitoring software, backup software, storage software and hosting software, all such that a user could run an instance of the service using the Service Source Code you make available." The breadth of that second sentence is the owners' risk call; this note does not adjudicate it. The FAQ says applications that merely use MongoDB as a database have no copyleft condition; that is the FAQ's statement, not the licence text.
4. **Conveying source only.** Section 4 (verbatim) and 5 (modified): the same notice and whole-work rules; no object-code section applies.

## The extension question
- **Corresponding Source (section 1):** "the source code needed to generate, install, and (for an executable work) run the object code and to modify the work ... For example, Corresponding Source includes interface definition files associated with source files for the work, and the source code for shared libraries and dynamically linked subprograms that the work is specifically designed to require, such as by intimate data communication or control flow between those subprograms and other parts of the work."
- **Reading, stated both ways, not decided:** if our shipped `mongod` is configured to load `meshvol_ext` by default, the extension is plausibly "specifically designed to require" and inside the Corresponding Source of the binary we convey; if the extension is a separate, optional download that the server only loads when an operator configures it, the plug-in reading (is the dlopen'd module part of one program) governs. The extension shares vtable structs and calls the host's function pointers across the boundary, which is the kind of "data communication or control flow" the clause names, but whether that makes it one program is a legal question I have not researched with a primary source (see below).
- **Aggregate (section 5):** "A compilation of a covered work with other separate and independent works, which are not by their nature extensions of the covered work, and which are not combined with it such as to form a larger program ... is called an 'aggregate' ... Inclusion of a covered work in an aggregate does not cause this License to apply to the other parts of the aggregate." An extension written to a MongoDB API is arguably "by [its] nature [an extension] of the covered work"; I state it, I do not resolve it.
- **FSF guidance (GNU GPL FAQ, `gpl-faq.en.html`, supplied by the user as a PDF on 2026-11-15; read with `pdftotext`).** It is about the GPL, not the SSPL. The SSPL is a GPLv3 derivative with a different section 13, and sections 1 and 5 above read the same way as GPLv3's, so I quote it as the standard reference, not as authority over the SSPL. The FAQ itself says the line between one program and two "is a legal question, which ultimately judges will decide."
  - GPLPlugins: "If the main program dynamically links plug-ins, and they make function calls to each other and share data structures, we believe they form a single combined program, which must be treated as an extension of both the main program and the plug-ins. If the main program dynamically links plug-ins, but the communication between them is limited to invoking the 'main' function of the plug-in with some options and waiting for it to return, that is a borderline case." and "Using shared memory to communicate with complex data structures is pretty much equivalent to dynamic linking."
  - Fork and exec: "A main program that uses simple fork and exec to invoke plug-ins and does not establish intimate communication between them results in the plug-ins being a separate program."
  - GPLAndPlugins: "If the main program and the plugins are a single combined program then this means you must license the plug-in under the GPL or a GPL-compatible free software license and distribute it with source code in a GPL-compliant way. A main program that is separate from its plug-ins makes no requirements for the plug-ins."
  - GPLStaticVsDynamic: "No. Linking a GPL covered work statically or dynamically with other modules is making a combined work based on the GPL covered work."
  - MereAggregation: "If the modules are included in the same executable file, they are definitely combined in one program. If modules are designed to run linked together in a shared address space, that almost surely means combining them into one program." and "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs ... But if the semantics of the communication are intimate enough, exchanging complex internal data structures, that too could be a basis to consider the two parts as combined into a larger program."
  - **Reading for us (a reading, not a conclusion):** our extension is `dlopen`ed into `mongod`'s address space and exchanges vtable structs and function pointers with the host (`MongoExtensionHostServices`, `MongoExtensionExecAggStage`, byte buffers). By the FAQ's criteria that is on the "single combined program" side, not the fork-and-exec side. By the FAQ's formula the extension would then have to be under "the GPL or a GPL-compatible free software license" and be distributed with source; section 5c makes the combined work SSPL, and each component only has to be under a licence that permits inclusion in an SSPL whole. Concretely: the `poc/gpu/extension/` adapter is already SSPL (owner decision), so no question there; a product extension would also statically link exactmesh (Apache-2.0) and patched Geogram (BSD-3-Clause), and whether those may sit inside an SSPL combined work is the one item this note marks "not verified". It gates shipping the extension at all, not only the Apache files staying Apache. The alternative that the FAQ calls separate is a separate worker process talking over a pipe or socket with simple, non-intimate messages; the MP14a plan already lists a subprocess worker for crash isolation. Whether it would also separate the licences is undecided: the FAQ's own test is semantic as well ("exchanging complex internal data structures ... could be a basis to consider the two parts as combined"), and triangle meshes as BinData plus per-document result documents may or may not count as complex internal data structures. That is exactly the part for the owners and counsel.
- **Section 7 (what we can add):** "You may place additional permissions on material, added by you to a covered work, for which you have or can give appropriate copyright permission." and "If additional permissions apply only to part of the Program, that part may be used separately under those permissions, but the entire Program remains governed by this License without regard to the additional permissions." So we can add permissions or a dual licence on code we wrote; we cannot grant a linking exception for MongoDB's own code or its headers.
- **Apache-2.0 and SSPL.** What the SSPL text says: the whole work is licensed under SSPL (section 5c). The FSF FAQ: "It means that the other license and the GNU GPL are compatible; you can combine code released under the other license with code released under the GNU GPL in one larger program." and "The GPL says that the whole combined program has to be released under the GPL." It does not list Apache-2.0 on that page (the FSF license list page was rate-limited, and I have not read it), and it says nothing about the SSPL. So: whether Apache-2.0 code may go into an SSPL whole is **not verified here**. Standing rules meanwhile: the Apache-2.0 files under `poc/gpu/` stay Apache-2.0 as separate works in this repo; exactmesh imports nothing from the fork tree, not even the public headers.

## Distribution channels
From search-result summaries (pages not opened by me): MongoDB withdrew SSPL from OSI review in March 2019, so it is not an OSI-approved licence; Debian said in December 2018 it would not carry SSPL software; Fedora legal listed SSPL v1 as not a free-software licence. This bears on whether we can use distro repositories, not on the obligations above. Sources: OSI "March 2019 License-Review Summary" (opensource.org/blog/licensereview032019); Fedora legal list thread (lists.fedorahosted.org); LWN <https://lwn.net/Articles/967081/>.

## Commercial licence
The FAQ names a commercial licence as the alternative ("Customers and OEM partners using MongoDB under a commercial license will not be affected by this change"). It does not say how to obtain one.
